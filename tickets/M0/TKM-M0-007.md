# TKM-M0-007 — Memory Service (CRUD + OpenAPI)

## Context

The MemoryUnit is the atomic primitive of
[[takumi-os-quantized-memory]]. Every captured event — Teams
meetings, Outlook emails, Jira issues, HubSpot opportunities —
flows through the Knowledge Acquisition Service
(TKM-M0-008 → -015), is quantised into a `MemoryUnit`, and is
persisted via this service. The Agent Platform
(TKM-M0-018 → -020) reads units back to assemble context for the
COO, Knowledge, and other agents.

This ticket is the **first .NET 9 service** in the monorepo. The
patterns established here — Clean architecture, MediatR +
FluentValidation, Cosmos partition-key tenant isolation, OpenAPI
3.1 at the docs/ root, kustomize base + overlays — are reused
verbatim by the other 8 services in M0 (per DIP §18).

## What this ticket delivers

- **Five .NET 9 projects** (Clean architecture, DIP §2.2):
  - `Takumi.Memory.Domain` — `MemoryUnit`, value objects, enums,
    `IMemoryUnitRepository`
  - `Takumi.Memory.Application` — MediatR commands/queries,
    FluentValidation, DTOs, `ApiResponse<T>` envelope
  - `Takumi.Memory.Infrastructure` — `CosmosMemoryUnitRepository`,
    `CosmosServiceCollectionExtensions`
  - `Takumi.Memory.Api` — `Program.cs`, `MemoryUnitsController`,
    `JwtTenantContext`, `GlobalExceptionHandler`,
    `CorrelationIdMiddleware`, Swagger
  - `Takumi.Memory.Tests` — domain + application + API tests
- **OpenAPI 3.1 spec** at `docs/api/openapi/memory.yaml` (matches
  the worked example in DIP §9.2; canonical source for client
  generation across C# / Python / TypeScript)
- **Dockerfile** (multi-stage SDK → ASPNET runtime, non-root user,
  healthcheck)
- **Kustomize base** at `src/k8s/base/memory/` (Deployment with
  Workload Identity, HPA, PodMonitor, ServiceAccount, Service)

## Approach

1. Build Domain layer first (no dependencies on Cosmos or ASP.NET)
2. Build Application layer (depends on Domain, defines
   `IMemoryUnitRepository`)
3. Build Infrastructure layer (Cosmos implementation)
4. Build Api layer (DI wiring, controllers, middleware)
5. Generate OpenAPI spec from the controller contracts (hand-written
   to match; in CI it will be regenerated by Swashbuckle)
6. Write tests: unit (domain invariants, validators), handler
   tests with in-memory fake, API tests with `WebApplicationFactory`
7. Write Dockerfile + kustomize manifests
8. Commit; update kanban + wiki handoff

## What this ticket does NOT deliver

- **Vector search** — TKM-M0-016 wires Azure AI Search (the index
  doesn't exist yet at M0 start; depends on TKM-M0-016)
- **Update / Delete endpoints** — MemoryUnits are write-once in M0;
  corrections flow through a new quantisation pass
- **Idempotency-Key enforcement** — header accepted, R1
- **Graph materialization** — best-effort links from extractors in
  M0; required and validated in M1 (after Neo4j lands per
  [[0002-knowledge-graph-neo4j]])
